Finding 3 · Admin authorization

Broken access control

Admin access is enforced only in the browser

High OWASP A01: Broken Access Control Backend: Medium effort
What happens today

The admin landing page checks user.is_admin in React and redirects non-admins to /cattle-info. That flag is populated by the client from getUserProfile(). The admin layout does no check at all, and the proxy at /api/proxy/[...path] forwards any path — including /v1/admin/* — to the backend with the caller's own token and no authorization logic.

So the browser UI is the only thing stopping a normal user from reaching admin data. Anyone can skip the UI entirely.

Exploit scenario
How it breaks

A regular authenticated user opens DevTools and runs
fetch("/api/proxy/v1/admin/users/").
The request carries their valid JWT and reaches the backend. If any single /v1/admin/* route is missing its role check, they read the full user list, toggle accounts, or export feed data — with no admin rights. The client "guard" was never in the request path.

Why the backend must own this

Client-side gating is cosmetic — the token, not the UI, is what the server sees. The only trustworthy control is a server-side role check on every admin route. is_admin must be derived server-side (from the DB or a verified JWT claim), never read from the request.

Backend changes (FastAPI)
  • Add a single admin dependency and attach it at the router level so no route can be forgotten.
  • Return 403 consistently for authenticated non-admins (not 404).
  • Audit every /v1/admin/* route to confirm coverage — there are ~18 in the client (users, feeds, feed-types, feed-categories, feedback, reports, export, bulk-upload, translations, languages, country-languages, feed-sync).
# deps.py
def require_admin(user: User = Depends(get_current_user)) -> User:
    if not user.is_admin:
        raise HTTPException(status_code=403, detail="Admin privileges required")
    return user

# admin_router.py — one guard covers the whole tree
admin_router = APIRouter(
    prefix="/v1/admin",
    dependencies=[Depends(require_admin)],   # every route inherits it
)

Router-level dependency is the key move: it guarantees a new admin endpoint is protected by default rather than by memory.

Frontend changes

None required for security — the backend is the control. Keep the existing is_admin UI gate purely for user experience (don't show admin screens to non-admins). No proxy change: the proxy can't verify roles without decoding the JWT, and that responsibility belongs on the backend.

How to verify
  • With a non-admin token: curl each /v1/admin/* route → expect 403 on all.
  • With an admin token: same routes → expect 200.
  • Add a regression test per route group so a future endpoint can't ship unguarded.

Finding 4 · Insecure Direct Object Reference

Identity trusted from the request body

Client-supplied user_id / report_id

High OWASP A01: IDOR Backend: Medium effort
What happens today

Several requests still carry a client-controlled identifier in the body or query rather than deriving it from the JWT:

  • POST /v1/animal/diet-evaluation-working — body includes user_id
  • save-report — body { report_id, user_id }
  • fetch-simulation-details — body { report_id, user_id }
  • insert-custom-feed / update-custom-feed — body user_id + feed_id

If the backend uses those values instead of the authenticated subject, a user can name someone else's identifier.

Exploit scenario
How it breaks

User A sends fetch-simulation-details with { report_id: <B's report>, user_id: <B> }. If the backend keys the lookup off the body values, A reads B's simulation — herd data, costs, contact details. The same shape lets A save or overwrite records under B's account.

Why the backend must own this

The client can stop sending the field, but that alone fixes nothing — an attacker crafts the request by hand. Authorization must be enforced where the data lives: derive identity from the token and verify resource ownership before acting.

Backend changes (FastAPI)
  • Derive user_id from the JWT (current_user.id) on every endpoint; ignore any body/query user_id entirely.
  • Enforce ownership on resource-scoped operations (report_id, feed_id): confirm the row belongs to current_user before reading/writing → else 404 (preferred over 403 to avoid confirming the resource exists).
def fetch_simulation_details(
    report_id: str,
    user: User = Depends(get_current_user),   # identity from token
):
    report = db.get_report(report_id)
    if report is None or report.user_id != user.id:
        raise HTTPException(status_code=404, detail="Not found")
    return report

Body user_id is simply never read. Ownership is re-checked server-side even though the client "knows" the id.

Frontend changes

Optional cleanup. Once the backend ignores body user_id, those parameters in src/lib/api.ts become dead weight and can be dropped (they are already documented as legacy shapes). Harmless to leave during the transition — the backend ignoring them is the fix; removing them is tidiness. I can do this frontend cleanup once the backend change is live and confirmed.

How to verify
  • As User A, request User B's report_id → expect 404.
  • Send a body user_id that differs from the token subject → server behaves as if it were the token's user (body value has no effect).

Finding 2 · Session token storage

Token exfiltration surface

JWT lives in localStorage — move it to an HttpOnly cookie

Medium OWASP A07: Auth Failures Backend + Frontend
What happens today

Login returns { token: { access_token } }. The PWA stores the JWT on the persisted user object in localStorage["rationsmart-storage"], and an axios interceptor attaches Authorization: Bearer <token> to every request. Anything running in the page can read that token.

Note: no XSS sink exists in the current code (no dangerouslySetInnerHTML, eval, or innerHTML), so this is a defense-in-depth hardening, not an active breach — but a single future XSS or a malicious dependency would turn it into full session theft.

Exploit scenario
How it breaks

Any injected script — a compromised npm dependency, a future XSS, a malicious browser extension — runs localStorage.getItem("rationsmart-storage"), lifts the JWT, and replays it from anywhere until it expires. An HttpOnly cookie is invisible to JavaScript, closing that path.

Why the backend must own this

Only the server can set an HttpOnly cookie — by definition JavaScript cannot create one. The backend must issue the token as a cookie on login and read it for authentication.

Backend changes (FastAPI)
  • On login and set-new-pin, set the JWT as a cookie: HttpOnly; Secure; SameSite=Lax.
  • Accept the token from the cookie in the auth dependency (fall back to the Authorization header during migration).
  • Add POST /v1/auth/logout that clears the cookie.
  • Because auth now rides a cookie, add CSRF protection (SameSite=Lax covers most; add a CSRF token for state-changing routes if SameSite must relax).
def login(payload, response: Response):
    token = issue_jwt(user)
    response.set_cookie(
        key="access_token", value=token,
        httponly=True, secure=True, samesite="lax",
        max_age=60 * 60 * 24, path="/",
    )
    return {"user": user, "requires_pin_reset": ...}
Frontend changes (required here)
  • Stop persisting the token in the Zustand store; drop the Bearer interceptor.
  • Proxy must relay cookies: the browser talks to vercel.app/api/proxy, not the backend host directly, so the proxy has to forward the Cookie header upstream and rewrite the upstream Set-Cookie domain to the Vercel origin. This is the main complication — the cookie the backend sets is scoped to 47.128.1.51, which the browser never sees.

This proxy-cookie translation is why #2 is an architecture change, not a drop-in. I'd handle the frontend/proxy half in lockstep with the backend rollout.

Lighter alternative (if cookies aren't worth the churn)

If the team decides the localStorage risk is acceptable given no XSS exists, a cheaper mitigation set: short access-token TTL + refresh tokens, a strict Content-Security-Policy to shrink the XSS surface, and strict dependency review. This reduces the blast radius without the cookie/proxy rework. Cookies remain the stronger end state.

How to verify
  • After login, the JWT appears in Set-Cookie (HttpOnly), and is absent from localStorage and JS-readable document.cookie.
  • Authenticated requests succeed with no Authorization header present.
  • Logout clears the cookie; subsequent calls return 401.

Frontend items already fixed (this session, separate from the above): production console-log stripping of JWT/PII, PIN removed from localStorage, proxy timeout + error-message hardening, security response headers, lint/typecheck/format tooling, and the grazing distance ≥ 1 contract. 810 tests passing.

Frontend-only, not requiring backend — npm/Next.js CVE bump (within 14.2.x), tsconfig target, lint warnings — tracked separately.
